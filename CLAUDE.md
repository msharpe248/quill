# Quill

Read `Quill Terminal Email Client Spec.md` at the start of every session. It is the source of truth, and its "Working rules for Claude Code" section applies to all work here. Then read `DECISIONS.md` for the choices made since.

The owner asked on 2026-11-15 for unattended work through M10 without waiting between milestones; acceptance steps that need them (real accounts, a developer account, App Review) are recorded in `DECISIONS.md` as not verified and passed over. While they are away, never run Quill against `~/Library/Application Support/Quill` (their real account and mail): use `--demo`, or scratch `--config-dir` and `--data-dir`.

M0 (core skeleton), M1 (shell spike), M2 (IMAP read), M3 (compose and send), M4 (rendering and media) and M7 (POP3) are built and accepted. The rest is built as far as it can be without the owner, and says in `DECISIONS.md` what was not verified:

- M5 (OAuth and Graph): built, tested against stand-ins only. A real sign-in and a real Microsoft 365 or Gmail mailbox need the owner; never contact a real provider while they are away. The form adds an account that signs in with Google as it does a Microsoft one (`Kind::Google`, 2026-11-16): an `imap` account with `auth = "oauth"`. Quill's own application with Google is the owner's registration, and is given to builds, never to the source (`oauth::GOOGLE_APPLICATION`, from `QUILL_GOOGLE_CLIENT_ID` and `QUILL_GOOGLE_CLIENT_SECRET` at compile time; `app/build-app.sh` reads them from `google-client.json`, which git ignores). Never write either half into a file that is checked in, a commit message, or anything printed. A build with it asks a Gmail address for nothing but the sign-in; one without (`cargo build`, `cargo test`, CI) asks for a client, and the tests hold either way. Saving such an account starts its syncing, which connects to its mail servers: a test or a scripted run must never save one whose servers are Google's.
- M6 (daily driver): search, the palette, the mouse, IDLE push, bulk actions, conversations, notifications, `mailto:`, spell check and the performance budgets are in. There is no App Store submission: see the next paragraph.
- M8 (P1 features): the headless CLI, saved searches, snooze, send later, rules, unsubscribe, templates, invitations and hooks are in. Hooks run only in a terminal: running them from the app has not been tried.
- M9 (Vim): the draft file, the plugin, the shell's side and the core's side are in. The editor is the user's own, with their own settings for it, in a terminal and in the app alike (2026-11-16): `editor` under `[compose]` is `vim`, `nano`, `pico` or `mg`, and `editor_path` names the program when it is not the one of that name on the `PATH`. In the app it runs in the message's own pane, under the fields, and has the text alone. `builtin` is the default. The app has no editor inside it.
- M10 (EWS): built, tested against a stand-in only.

On 2026-11-16 the owner chose to give Quill out as source and as a download (GitHub, Homebrew) and not through the App Store, and to drop the App Sandbox with it. What the spec says of the sandbox, entitlements, App Review and a bundled or imported Vim is superseded by "Out of the sandbox" in `DECISIONS.md`. The app and a terminal's Quill are one mailbox now, and only one may have it open (`hold_mailbox` in `quill-cli`, `open.lock` in the data folder).

What each milestone left undone is listed under it in `DECISIONS.md`.

The milestones are history now (`docs/roadmap.md`), and are kept out of `README.md` (2026-11-17). The README says what Quill does in the release as it stands, how to get it and how to report a problem, and is written to be read by someone deciding whether to try it: current, factual, nothing claimed that is not so. How each thing is used goes in `docs/manual.md`, building and checking in `docs/development.md`, what is next and what is missing in `docs/roadmap.md`. A change a user can see updates the manual, and the README too when it changes what Quill can be said to do.

Quill is public at https://github.com/msharpe248/quill since 2026-11-16, under the MIT License with the Commons Clause (`LICENSE`). `main` is what is published, and is where work goes now; the milestone branches (`m2-imap-read`, `m3-compose-send`, `m4-rendering-media`) are local history and are not pushed.

Commit finished, checked work as you go, locally. Push only when the owner says to: a push is public. Before any commit, `git config user.email` must be the owner's GitHub no-reply address, and nothing checked in may carry their own address, their employer's name, either half of the Google client, or anything about their own accounts and mail.

## Checks

A change is not done until these pass:

```sh
cargo fmt --all --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
cargo deny check
(cd app && swift test && swift format lint --configuration .swift-format -r Sources Tests Package.swift)
```

For anything visible in the app, also build it and look: `app/build-app.sh`, then run it with `--script` and `--dump-screen` (see `docs/development.md`) and read the text and the `.png` it writes.

## This machine

- Rust comes from Homebrew's keg-only `rustup`; if `cargo` is not found, put `/opt/homebrew/opt/rustup/bin` on `PATH`.
- A scratch local mail server for trying things by hand: see how `crates/quill-imap/tests/common/mod.rs` starts Dovecot unprivileged. Its directory needs a short path (sockets). Always stop it and remove its Keychain entry afterwards (`security delete-generic-password -s Quill -a "imap:USER@HOST"`).
- The POP3 tests use the same Dovecot, through `crates/quill-pop3/tests/common/mod.rs`.
- No SMTP server is installed. To try sending by hand, a few lines of Python that accept one SMTP conversation and write the message to a file are enough, with `tls = "none"` on `127.0.0.1`. Never point a scratch account at a real server.
- A Keychain item belongs to the build that made it. After any rebuild, a `quill` or `Quill.app` that reads an item an older build saved makes macOS put a dialog on the owner's screen, and Quill waits on it silently. For a scratch run: delete the scratch item, then save it again (or add the account again) with the build you are about to run, and do not rebuild in between.
- The app is not sandboxed, and keeps its settings and mail where a terminal's Quill does: `~/Library/Application Support/Quill`. So `Quill.app` started with nothing said opens the owner's real mailbox. Every scripted or scratch run of the app says where to work, all three: `--demo` or a scratch mailbox, `--core-env QUILL_CONFIG_DIR=...`, `--core-env QUILL_DATA_DIR=...`, and `--core-env HOME=...` with the app itself started under `env HOME=...` (the editor it runs is the owner's own, and would otherwise read and write their vimrc and viminfo). Set the scratch path in a statement of its own and check it is not empty before using it: an empty one points the run at `/`.
- A scratch run that is to be reached by `quill` commands or `quill mcp` needs a data folder with a short path: the door is a socket file in it (`agent.sock`), and a socket's path may be about a hundred characters. The session's scratchpad is too deep; a folder straight under `/private/tmp/claude-501/` is short enough. The demo mailbox opens a door only when it is given a data folder (`--data-dir`, or `QUILL_DATA_DIR`).
- The IMAP tests need Dovecot (`brew install dovecot`, already installed here). They start their own server per test; nothing runs in the background.
- `xcodebuild` fails with "failed to load a required plug-in" until the user runs `xcodebuild -runFirstLaunch`. `swift build` and `swift test` do not need it.
- If a build ever stops with "You have not agreed to the Xcode license agreements", that needs the user (`sudo xcodebuild -license`); `export DEVELOPER_DIR=/Library/Developer/CommandLineTools` builds meanwhile.

## Conventions the code already follows

- `update` in `quill-tui/src/state.rs` is the only place UI state changes. Views take `&State`. It returns `Effects` (store requests and host requests) for the run loop to perform.
- The UI task never touches disk. It sends a `DataRequest` to the store worker (`quill-tui/src/data.rs`) and gets `DataEvent`s back.
- `quill-tui` reads no files. `quill-cli` loads config, theme and keys and passes their contents in.
- Every user action is a command in `quill-tui/src/command.rs`. Adding one means: the registry entry, its keys in both presets in `keymap.rs`, a hint if it deserves one, the manual's tables (`docs/manual.md`), and tests. The app's menus and toolbar pick it up from `commands.list` by themselves.
- The shell holds no mail logic. It knows command names, titles and keys. If Swift needs to know what a message is, add a command or a bridge message instead.
- Only `app/Sources/TerminalKit` imports `GhosttyTerminal`. Everything else uses the `TerminalSurface` protocol.
- A bridge change touches `schema/bridge.json`, `schema/examples`, `crates/quill-host/src/bridge.rs` and `app/Sources/Bridge` in the same change.
- The core's terminal is put in raw mode and sized by `TerminalKit`, from the PTY's master side (`rawTerminal`). It was built so for the App Sandbox, where a program may not change its terminal's modes, and is still how the core runs. Do not "fix" the core to set raw mode itself. An editor is started without it, and sets its terminal's modes for itself.
- The reader draws a message's HTML from the raw message (`Store::raw`), laid out for the pane's width by `quill_mime::html::render`. Mail is untrusted: every span is sanitized before drawing, and nothing is fetched.
- Only `quill_core::links::is_openable` decides what may be opened or written into a terminal hyperlink. The shell has the same rule in `Links.isOpenable`; change them together.
- Link text is marked as a hyperlink by the run loop, not by views: the reader returns `LinkPlacement`s. Only underlined link text is marked; keep it that way, or a cell can keep a stale link.
- Where there is typing to do (`Context::Setup`), a key goes to the field first and to a command only if the field has no use for it. A new typing context follows the same rule in `State::on_key`.
- The form that adds an account, and each question Quill asks before going on (a sign-in, an existing account's certificate, a time to snooze until or send at, unsubscribing), is one state machine in the core with two views: drawn in the terminal, or, where `Env::sheets` is set (the app), described to the shell (`State::form` in `state/sheet.rs`, which asks the state in front for its `form`; `form.show`) and shown in the one sheet, whose buttons come back as `form.used` (`State::on_form`, which answers only the form on show at the step it names, and ends where the terminal's keys do). A change to one goes in its state and both views, with the words shared; nothing about it is decided in Swift, which knows fields by kind and never by name. A new one needs a step name no other shares, and its terminal keys switched off while the sheet has it (`State::answered_in_sheet`). What is chosen from with the keyboard is never a sheet: the palette, the pickers (folders, templates, links, attachments, hooks, spellings) and the help.
- What a form shows to be read off and carried elsewhere (a sign-in code, the page to type it at) is a `code` field, a `bridge::Secret` like a password: neither side prints it or writes it to a dump.
- A password crosses the bridge only in `form.used`, under `secrets`, in a type that does not print (`bridge::Secret`, `FormSecret`). The core never sends one back, and nothing logs or dumps one: keep it so when adding a log line or a dump line near the bridge.
- The UI adds accounts through a service it is handed (`AccountsLink`, implemented in `quill-cli/src/service.rs`); it reaches no server, Keychain or config file itself.
- `config.toml` is changed for the user only through `quill-cli/src/config_edit.rs`, which keeps their comments and refuses to write a file Quill could not read back.
- The app's Settings window is described by the core and drawn by the shell. Which settings it has, their panes, labels, allowed values and help are in `quill-tui/src/settings.rs`, by the names `quill-core/src/config.rs` reads the file with. Adding one means: `Setting` (key, section, pane, whether it holds at once), its field in `describe`, its arms in `change` and `Change::written`, `Settings::of`, `Applied` if it holds at once, the manual's table (`docs/manual.md`), and tests. The shell knows a field by its kind and nothing more; a new kind is a bridge change.
- The Settings window's file work is the accounts service's (`quill-cli/src/settings.rs`): every request reads `config.toml` from disk, a change goes through `config_edit::set`, and the answer is the file read again. Nothing of the config is kept between requests, so a hand edit is never written over, and a file with a mistake in it is never written at all.
- The user's own keys are changed in Settings > Keys (the app only): the pane lists the registry with the keys in force (`settings::keys`), a key is pressed into a `keys` field of a sheet (`KeysPrompt`, `Context::RecordKeys`; the shell's `KeyRecorder` writes it as `KeyNotation.written` does, which must stay what `KeyChord::from_str` reads), and the service writes `keys.toml` (`AccountRequest::Keys`, `keys_edit::apply`), never over a file it could not read. Whether a key can be had is decided in `KeysPrompt::verdict` and nowhere in Swift. A new command is in the pane by being in the registry.
- A theme is made, changed and deleted in Settings > Appearance (the app only): the pane lists the themes as the service read them (`ThemeLine`), a theme's colours are picked in the `color` fields of a sheet (`ThemePrompt`, `Context::EditTheme`, in `state/themes.rs`), and the service writes and deletes the files (`AccountRequest::Themes`, `quill-cli/src/theme_edit.rs`). While the sheet is up Quill is drawn with the theme being made (`Look::trying`), which only `State::follow_theme_draft` asks for and only the run loop sets. A colour the theme leaves to the terminal stays so unless another is picked: what a well comes back with is compared with what it was shown. What a theme may be called is decided in `ThemePrompt::refused` and checked again where the file is written; a theme Quill comes with is never saved over. A new colour a theme can have is a `Slot`, and is in the sheet and the file by being one.
- The font of the app's terminals is `font` and `font_size` under `[ui]`, sent in `state.update` and applied by `TerminalKit` to every terminal at once. Which fonts there are is the shell's to say (the `font` field kind, `FixedPitchFonts`). The size is held to 6 to 72 and the name to one line in the config, on the bridge and in `TerminalKit`: the name becomes a line of libghostty's configuration.
- `Env` is changed in one place: the run loop puts `Effects::settings` into it (`Applied::apply`) between one update and the next, for the settings that hold at once. `update` still takes `&Env`, decides, and changes only the state. A harness that runs `update` does the same (`tests/common/mod.rs`).
- Closing the main window does not quit the app or stop the core (2026-11-16): it is brought back with `showMainWindow`, never `showWindow`, which starts the core. Only quitting stops the core (`mustWaitForCoreBeforeTerminating`). Anything that assumed "no window means no app" is wrong now.
- `q` is `window.close` and `Q` is `app.quit` (2026-11-17). In a terminal both quit. In the app (`Env::window`) `window.close` only asks the shell to close the window (`HostRequest::CloseWindow`), which is the red button's close: the core is not stopped. Anything that must happen when Quill really ends belongs with `should_quit`, not with the window closing.
- The edges between the panes are dragged in the core (`layout::divider_at`, `layout::dragged`, `State::resizing` in `state/mouse.rs`), and where they are left is `sidebar_width` and `reader_width` under `[ui]`, remembered through the accounts service. Every width the layout works out goes through `layout::Split`: the config's, or what was dragged in this run. Moving the accounts' edge keeps the message's columns. The edge between the list and the app's reading pane is the shell's own divider and is not the core's to move.
- The settings window is resized at once, never animated, and its toolbar is never hidden: either runs AppKit's event loop in the middle of a change, and ended in an exception when the panes were put back (see `DECISIONS.md`).
- While a message is written, keys go to `Compose::key` first; a compose command needs a `ctrl` key as well as a `cmd` one, because a terminal keeps `cmd` for itself. Hints come from `Env::hint_key`, which names the key that works where Quill is running.
- The app's Edit menu items Cut, Copy and Select All run the core's `edit.*` commands while those are enabled and act on the focused view otherwise. A shell menu item that should always work needs an explicit target: a disabled item still swallows its key.
- The embedded terminal has no key bindings of its own (`keybind = clear` in `GhosttySurface`). Keep it so, or libghostty takes `cmd` keys before the menus and the core.
- Files reach the core from the shell as `files.dropped` with copies in the app's temporary folder; the core deletes each copy once read. The clipboard is written through `Host::copy_text`.
- A scripted run puts a colour in a sheet's well with `sheetset:` and never clicks one: a click opens the Mac's colour picker, which is a panel.
- A scripted app run must never show a panel, open a browser or touch the clipboard: `DebugScript` replaces `filePicker`, `linkOpener` and `clipboardWriter` with recorders. Add a recorder with anything new that reaches outside the window.
- Images are placed by the run loop, not drawn by views. A view leaves cells empty and returns an `ImagePlacement`.
- UI changes show up in the insta snapshots under `crates/quill-tui/tests/snapshots/`. Regenerate with `INSTA_UPDATE=always cargo test -p quill-tui`, then read the diff.
- What an account signs in to a mail server with comes through `quill_core::Credentials` (async): a Keychain password read off the async threads, or an OAuth token. Do not add a blocking secret lookup to a backend.
- OAuth lives in `quill-auth`; which provider and application an account uses is decided in `quill-cli/src/oauth.rs`. The core never opens a browser: the sign-in address goes to the UI, which hands it to the host.
- The sync engine goes by `Backend::capabilities`, not by account type. A backend with no folders (POP3) has its mail kept in the store: local folders with ids starting `kept:`, local moves and marks, every body downloaded, and nothing deleted from the server that is not filed here in full.
- An action on several messages is one `DataRequest::Many`, and its queued operations are grouped (`Store::group_operations`) so one undo takes them all back.
- Run tests with `--no-fail-fast`: a failure in one test binary otherwise hides stale snapshots in the next.
- A question drawn over the panes (sign-in, a time, unsubscribe, a picker) is a `Context` of its own with its state in an `Option` on `State`; the bridge has fewer contexts, so `app.rs` maps a new one onto the nearest existing one. Movement commands apply only where there is something to move in.
- Things that wait on the user or the network for long (a sign-in, a one-click unsubscribe) run in the accounts service beside its other requests, and report back as `AccountEvent`s.
- New mail is announced from `SyncEvent::Arrived`; rules for arriving mail run in the engine (`quill-sync/src/rules.rs`) and act through the same queue as the user.
- A scripted run of the app never asks for notification permission, never posts a notification and never shows an alert: recorders stand in (see `DebugScript`). It keeps the settings window's last pane for the run only (`TransientSettingsPaneMemory`), as it does the reading divider.
- When two sessions or agents edit the tree at once: per-crate `cargo fmt -p`, never `--all`; stage by path; and a bridge change is committed with both of its sides.
- A program Quill starts (the terminal's Vim, a hook) is an argv built from constants and paths, never a line for a shell, and nothing from a message is ever part of it. What a message says reaches a program only as a file, standard input, or a cleaned one-line environment value.
- The shell starts two programs: the core, from its bundle, and the user's own editor, with the command the core gives it (`pane.editor`'s `argv`: the program by its absolute path and its arguments, never a line for a shell). The core finds the program (`vim::find_program`: what `editor_path` or `QUILL_VIM` names, else the editor's name on the `PATH`) and makes the command (`vim::command`), the same for a terminal and for the app; the shell adds nothing to it. Both are given the app's environment with Homebrew's two folders after its `PATH` (`ProgramEnvironment`).
- Any editor the app runs is the owner's real one, with their real settings, unless the run has a home folder of its own (see "This machine").
- In the app an editor outside Quill runs in the text's place in the message's pane (`Compose::embedded`): the file it is given is the text alone (`vim::Share::Body`, with `body-only` in the draft's folder), the fields stay live in the core's terminal, and nothing in the file is read as a field. Where it goes and whether it has the keys is the core's to say (`State::editor_spot`, sent as `editor.place` by the run loop when it changes); the shell lays the editor's terminal over those cells (`TerminalStack`, `EditorOverlay`) and decides nothing. In a terminal the editor still has the whole screen and the whole message.
- The plugin does not use `delete()`, `rename()` or `mkdir()` (it empties the `command` file instead of deleting it): a restricted Vim refuses them, and the real-Vim test runs with `-Z` to hold that.
- An editor that is not Vim has none of Quill's commands in it: it is started with its cursor on the body's first line (`+LINE` in its arguments), asked to leave in its own keys (`PoliteStop`), and Send and Save are off until the message is back.
- Vim is always started with `vim::NO_MODELINES`, in a terminal and in the app: there is one place that makes the command.
- Web reading (`view.web_reading`, `[ui] web_reading`) is a mode of `State`: the reader's state still follows the list, it is just not drawn. The page for the host's reading pane is asked for in one place, `State::follow_selection`, at the end of every `update`, only once the run loop has said the cursor rested (`Action::SelectionSettled`), and a page is shown only while `Follow::asked` still names it. Nothing else asks for a reading page, except `i` and `I` asking again for the one on show.
- What the reading pane says about its page (remote pictures left out) is `notice` in `reading.show`: the core's words, and buttons that are commands by name and come back as `command.run`. The shell draws the bar and decides nothing; a new thing to say about a page goes there, not in the status line.
- A choice made in the UI that outlasts the run goes to the accounts service as `AccountRequest::Remember`, which writes `config.toml` through `config_edit`. The demo mailbox has a service that does only that (`service::spawn_remembering`).
- The accounts pane can be hidden (`view.sidebar`, `State::sidebar_hidden`, `sidebar` under `[ui]`). Hidden or in a narrow terminal it has no columns and is drawn over the other panes while it has the keys: `layout::sidebar_floats` is the one test for that. `tab` goes between the list and the message only; the accounts are on `shift-tab`.
- Nothing is set up or imported for an editor: it reads the user's own settings from their own home. What the settings window has for it is which editor (`editor`) and, for any but Quill's own, which program (`editor_path`, a text field under it). Emptying a text setting takes its line out of the file (`Written::Gone`).
- The list of every key has two views: drawn over the panes (`K`, `f1`, and always in a terminal), and in the app's own floating window when asked for from a menu (`Action::Command(HelpKeys)` where `Env::keys_window` is set, sent as `keys.show`). The window shows `keys.list`, which the run loop sends beside `commands.list`: both come from `view::help::all_lines`, so a change to the list changes both.
- A command that is on or off says so through `State::is_on`; the bridge carries it as `checked` in `state.update` and the shell checks its menu item. The shell never works out a mode from anything else.
- The app's terminals (Quill's own and the editor's, laid over it) take their default background and foreground from the core's theme, sent in `state.update`. In `TerminalKit` they go into libghostty's theme, not its configuration: the library lays its theme over the configuration, and a colour set only there does not hold.
- Removing an account (`account.remove`, Remove… in Settings > Accounts) is two steps, and the first changes nothing: the accounts service says what would be lost (`AccountRequest::RemoveAsk`, counted in the store by `Store::account_leftovers`), the user is asked with that said (`RemovePrompt`, a `Context` of its own; `y` in a terminal, a sheet with no default button in the app), and only then does the service do it all (`AccountRequest::Remove`): the settings file first, and if that cannot be written nothing else; then the engine stopped, the store's copy deleted and the secrets no other account shares taken out of the Keychain. The UI removes nothing itself and lets go of the account when it hears it is gone (`state/remove.rs`).
- Changing an account (`account.edit`, Edit… in Settings > Accounts) is the form that adds one, opened on the account as the service says it is (`AccountRequest::EditAsk`, then `Setup::editing`): it starts at the servers, the name and the kind are not shown or taken from an answer, and an empty password means the one kept. The service tries the settings (`VerifyChange`) and writes them (`Change`, `config_edit::change_account`), moves the password to the name its new settings give it, and puts the account in the engine in place of what it was. Only an IMAP account with a password is changed this way; the service refuses the rest with the reason. A change to the add form is a change to this one: check both.
- An account given to the engine again (`set_account` over one that is running) stops reading at once, but its queue runner is never cut off: it finishes what it has in hand and ends (`Running::retire`), and the new one waits for it. Mail that was waiting is hurried by the engine then, and by nothing sooner: made due while the old runner lives, it is taken by the old settings. Do not hurry an account's sends from outside before handing the account over.
- Mail that cannot go for a reason that may pass (no server answering, no server to send through) waits in the Outbox with the reason and a time to look again; only what a server refused is `failed` and waits for the user. `compose.send` with no message being written sends the Outbox message the list is on (`DataRequest::SendNow`).
- A folder whose id starts `kept:` is in the store and on no server; one the user made is `kept:folder:NAME` (`quill_store::is_kept`, `is_made_here`). Any account may have them. A message in one is named `kept:HASH` and its bytes in the blob store are the only copy: never evict, drop or overwrite them, and never tell a server to delete a message before `Engine::whole` has said its bytes are here. A move between a server folder and a local one is `QueuedKind::Keep` or `QueuedKind::Upload`, not `Move`; `retain_folders` never removes a folder made here.
- Wherever a folder is named to the user, a local one is said to be: under the accounts pane's "On This Mac" heading (`SidebarEntry::OnThisMac`, which the cursor skips), or with `ON_THIS_MAC_SUFFIX` after its name. A new place that names folders does the same.
- Where a message was before Quill moved it to a trash folder is noted (`Store::note_trashed`) by whatever deletes to the trash; `message.put_back` reads it. A new way to delete to the trash notes it too.
- A theme is a file in `themes/`: `NAME.toml` is Quill's own, any other name is one written for Ghostty, called what the file is called. What a Ghostty palette comes to is worked out in `quill-tui/src/theme/ghostty.rs` and held to the contrast bars in `theme/contrast.rs`; the sweep over the installed Ghostty themes must keep passing. The shell reads a theme file only for the chooser's patch of colours and copies it in (`app/Sources/Themes`); whether it is a theme is the core's to say (`setup::load_theme`).
- `Env::styles` is made from `Env::look` (the appearance, what the host says the Mac is, a theme for each) by `Env::restyle` and nothing else. The app's own windows follow `appearance` in `state.update`. A scripted run never asks what the Mac looks like and never changes it: `system:dark` and `system:light` pretend.
- What can be done to the mail from outside Quill's window is in `quill-tui/src/agent` and nowhere else (2026-11-17; `Quill Agents Spec.md` is the design). The commands for a shell and the MCP tools are two fronts over it: a `Call`, checked against `[agent]` in the config (`AgentConfig`), carried out by `agent::perform` through the same store queue the UI uses, and written in the store's log (`agent_log`). Adding an action means: the `Call` variant, its entry in `tools::TOOLS` (name, level, hint, arguments), its arm in `Call::parse`, the code in `look.rs` or `change.rs`, the command in `quill-cli/src/main.rs`, the manual, and tests; then `QUILL_UPDATE_SCHEMA=1 cargo test -p quill-tui --test agent_schema` and read what changed in `schema/agent.json` and `schema/examples/agent`.
- Three things hold for every action there, and a new one keeps them: what a message says goes out as data in fields of its own and is never acted on; nothing deletes for good (`delete` is a move to a trash folder, and where the UI's delete would be for good it is left alone and said to be); and nothing reads a secret, changes an account, writes the config, or touches rules or hooks. An argument a tool does not take is refused, never passed over: a misspelt `dry_run` must not be a change.
- A change made that way records how things were (`Done::undo`), so `quill undo` can take it back long after `U`'s ten seconds. A new kind of change says how it is taken back, in `change::undo`, or says that it cannot be.
- The Quill that is running is the one writer. A request from outside reaches it through the door (`quill-cli/src/door.rs`: a socket file in the data folder, the user's alone, with whoever connects asked of the system), becomes an `AgentAsk` for the run loop, and is done on the store worker's thread as `DataRequest::Agent`; what the UI is to hear comes back as ordinary `DataEvent`s, and the answer as `DataEvent::AgentDone`, which the run loop takes and the state never sees. With no Quill running a shell command works on the store itself (`act` in `main.rs`); MCP does nothing then, on purpose. Nothing listens on the network: do not add a port.
- The skill that teaches an agent the shell commands is one file, `skills/quill/SKILL.md`: compiled into `quill` (`quill skill show`), copied into the app's bundle by `app/build-app.sh`, and linked into agents' own folders by `quill skill install` (`quill-cli/src/skill.rs`). A test holds that every action in `tools::TOOLS` is shown in it as a command, and that its frontmatter is only what every agent's program takes; a new command goes in the skill with it. It approves no command ahead of the user (no `allowed-tools`). An install replaces a link or a copy it made, and never anything else.
- A test that runs `quill` says where the mailbox is in the environment (`QUILL_CONFIG_DIR`, `QUILL_DATA_DIR`), never in flags after the arguments, and so does a run by hand: a flag that is lost (after `--`, or swallowed by an argument) leaves the command on the owner's real mailbox. This happened once (2026-11-17, a search; see `DECISIONS.md`).
- `quill mcp` (`quill-cli/src/mcp.rs`) is a relay: it speaks MCP on its standard input and output and asks the running Quill for everything through the door. It holds no mailbox and decides nothing. It speaks the revisions of MCP that greet (`initialize`, up to 2025-11-25) and answers the newer `server/discover` as an unknown method, which that revision says sends a client back to the greeting. Check the current specification before changing it; do not go by memory.
- Mail sent from outside the window is marked with who sent it (`drafts.agent`), keeps the user's wait between messages (`send_gap`, counted from `agent_log.due`), and may be held (`DraftState::Held`), which only the user lets go (`Store::send_now`). A draft is changed or discarded from outside only if it was written from outside: the user's own writing is never lost to an agent.
- Stop Agents (`agents.stop`, `State::stop_agents`) switches both ways in off in `Env` at once (`Effects::agents_stopped`, which the run loop and any harness apply), writes it to the config (`Preference::AgentsOff`), hangs up on whoever is connected (`AgentLink::hang_up`) and takes back agent mail that has not gone (`DataRequest::AgentsStop`). Nothing an agent can ask for starts the agents again, or reaches `[agent]` at all.
- What agents do is told to the user by `notify` under `[agent]` (`State::on_agent_notice`); an MCP connection is always told (`State::on_agent_connected`), whatever that says. Their notifications' names start `agent.`.
- Fixtures use invented people at example.com. Never real mail, never real addresses.
